Для каждого поискового запроса считаем 10 самых частых следующих запросов (теги):
логи в ClickHouse → Go-сервис `/api/tags` → страница на `html/template`.

## Как запустить

```bash
docker compose up -d                                  # ClickHouse
for f in 01_create_logs 02_load_logs 03_build_tags 04_checks; do
  docker compose exec -T clickhouse clickhouse-client -u app --password app --multiquery < sql/$f.sql
done
go run ./cmd/server                                   # http://localhost:8080
go test ./...                                         # тесты
```

Файл `logs.parquet` должен лежать в `data/` (монтируется в контейнер как `user_files/data`).
Переменные окружения сервиса: `CLICKHOUSE_ADDR` (по умолчанию `localhost:9000`),
`CLICKHOUSE_DB`, `CLICKHOUSE_USER`, `CLICKHOUSE_PASSWORD`, `PORT` (по умолчанию `8080`).

## Таблицы и ORDER BY

- `search_logs`: `MergeTree`, `ORDER BY (user_id, timestamp)`. Расчёт идёт по цепочке запросов каждого
  пользователя в порядке времени, поэтому данные лежат так же и сортировка при расчёте не нужна.
- `query_tags`: `MergeTree`, `ORDER BY (query, rank)`. Сервис ищет по `query` и отдаёт по `rank`,
  то есть читает один подряд идущий кусок индекса.
- Типы: `DateTime64(3, 'UTC')` (порядок событий внутри секунды), `UInt64` для `user_id`, `String`
  для запроса. `Nullable` не нужен: в данных нет `NULL`.

## Данные и допущения

- Загружено 992 318 строк за 12–18.10.2026, 50 078 пользователей. Пустых запросов, `NULL` и точных
  дублей нет. «Грязь» только в регистре и пробелах: после нормализации уникальных запросов 2 632
  вместо 11 018.
- Нормализация: `lowerUTF8`, `\s+` → один пробел, обрезка краёв. В Go то же самое
  (`strings.ToLower` + `\s+`). Неразрывный пробел и «ё/е» не трогаем.
- Пары строятся по нормализованным запросам, пустые отбрасываются до построения пар.
  Интервал «не больше 30 минут» включительно. Событие с тем же временем упорядочено по тексту.
- Пользователи считаются точно (`uniqExact`), порог `users >= 5` включительно.
  Ничья по числу пользователей решается по алфавиту, чтобы результат был стабильным.
- API отдаёт массив `[{"tag": "...", "users": N}]`; если тегов нет, то `[]` и статус 200.
- Пересчёт тегов делает `TRUNCATE` и заполняет таблицу заново: на время пересчёта сервис видит пустую таблицу.

## Бонус: ежедневный пересчёт без «с нуля»

1. Храним не готовые топы, а **промежуточные агрегаты по дням**: таблица `AggregatingMergeTree`
   с полями `day, query, tag` и состоянием `uniqExactState(user_id)`. Уникальные пользователи по
   разным дням не складываются (один человек мог искать в оба дня), а состояния `uniq` объединяются
   (`uniqExactMerge`) без потерь.
2. Каждый день обрабатываем только новые данные: берём события нового дня плюс «хвост» последних
   30 минут предыдущего дня (чтобы не потерять пары на стыке суток), строим пары тем же запросом и
   пишем агрегаты за этот день. Повторный запуск того же дня безопасен: партицию дня сначала удаляем.
3. Топ-10 пересобираем из агрегатов за нужное окно (например, 30 дней): это небольшая таблица,
   считается за секунды. Старые дни удаляем по `TTL` или `DROP PARTITION`.
4. Готовый результат пишем во временную таблицу и подменяем атомарно (`EXCHANGE TABLES`),
   чтобы сервис никогда не видел пустую таблицу. Запуск по расписанию (cron или планировщик).
